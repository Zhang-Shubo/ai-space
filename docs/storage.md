# Storage design

The storage service is the Space-layer answer to "where does an app keep its data". It covers three things that every app otherwise solves on its own: a relational database, a place for large files (images, video, exports), and backups of both. Apps declare what they need in `space.yaml`; ai-space provisions it, hands the app a connection string, and keeps the copies.

Status: the database half is implemented in `src/space/storage/` (client, migrations, manifest section, provisioning, `space.env`, API, `env` command). Blob stores are provisioned and handed over (`storage.blobs` in the manifest, `BLOB_URL` plus `S3_*` credentials in `space.env`); the managed blob API on top (index table, streaming routes, presigning) and backups are design only. The scheduler's own store (`src/space/scheduler/store.ts`) still uses `bun:sqlite` directly and moves onto the client in a later change.

## Goals and non-goals

Goals:

- One database client for SQLite and PostgreSQL, so an app is written once and the backend is a deployment choice. SQLite is the default and needs no server.
- One blob store for files that do not belong in a database, with a local filesystem backend and an S3-compatible backend (AWS S3, Cloudflare R2, MinIO, Backblaze B2).
- Backups that run without anyone remembering: scheduled through the scheduler, stored in the blob store, verified, and restorable with one command.
- Apps in any language can participate. The contract is a connection URL and a directory or bucket, not a TypeScript library.
- Small machines stay viable. Nothing buffers a whole file in memory; SQLite adds no resident process.

Non-goals:

- An ORM or query builder. The client runs SQL. Portability comes from a short list of rules, not from an abstraction layer.
- Multi-machine replication or a distributed database. One workspace, one machine, one primary copy.
- Image processing, transcoding, or CDN features. The blob store stores bytes and serves them.
- MySQL. Bun's client supports it, but nothing here is tested against it.

## Overview

```
app  ──(DATABASE_URL)──►  database   sqlite file | postgres database
app  ──(BLOB_URL)──────►  blobs      <workspace>/data/<app>/blobs | s3://bucket/<app>/
scheduler task ────────►  backup     snapshot ─► compress ─► blobs://backups/<app>/…
```

Three modules under `src/space/storage/`:

| Module | Responsibility |
| --- | --- |
| `db` | Open a database by URL, run migrations, expose the dialect. Provision per-app databases. |
| `blobs` | Put, get, list, delete, presign. Filesystem and S3 backends behind one interface. Metadata index. |
| `backup` | Snapshot databases and filesystem blobs, upload, prune, verify, restore. |

The API surface for apps is deliberately thin: two environment variables and a handful of HTTP routes. ai-space's own services use the TypeScript modules directly.

## Workspace layout

```
~/.ai-space/
├── data/
│   ├── space.db                 ai-space's own database (scheduler, blob index, backup log)
│   ├── blobs/                   filesystem blob backend for ai-space itself
│   └── <app>/
│       ├── main.db              provisioned SQLite database (one file per declared name)
│       ├── blobs/               provisioned filesystem blob store
│       └── space.env            provisioned variables the app process loads
├── backups/                     staging area for snapshots before upload; emptied after
└── .env                         SPACE_* configuration, S3 credentials
```

`space.env` is generated by ai-space and never edited by hand. It holds `DATABASE_URL`, `BLOB_URL`, `SPACE_APP_DATA_DIR` and, for S3, the credentials the app needs (`S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, the names Bun's `S3Client` and most SDKs read by default). An app's systemd unit loads it with a second `EnvironmentFile=` line; a command target run by the scheduler gets it merged automatically, the same way the app's `.env` is merged today.

## Databases

### Backends and configuration

A database is identified by a URL. The scheme selects the backend:

| URL | Backend |
| --- | --- |
| `sqlite:///abs/path/app.db` | SQLite through Bun's built-in client (`bun:sqlite` underneath). Default. |
| `postgres://user:pass@host:5432/db` | PostgreSQL through Bun's built-in client. No driver dependency. |

`SPACE_DB_URL` sets ai-space's own database (default `sqlite:///<workspace>/data/space.db`). Per-app databases follow the app's `space.yaml` declaration (see [Registering](#registering-storage-in-spaceyaml)): `sqlite` yields `<workspace>/data/<app>/app.db`; `postgres` creates a database named after the app on the server given by `SPACE_PG_ADMIN_URL`, with its own role and password, and writes the resulting URL into `space.env`.

### Client

```ts
const db = await openDatabase(url);          // { sql, dialect: "sqlite" | "postgres", close() }
await db.sql`INSERT INTO notes (id, body) VALUES (${id}, ${body})`;
const rows = await db.sql`SELECT * FROM notes WHERE id = ${id}`;
await db.sql.begin(async (tx) => { /* transaction */ });
```

Bun's `SQL` class provides the tagged-template interface for both backends, so parameter binding is identical and injection-safe by construction. The wrapper adds three things: the dialect tag, SQLite pragmas on open (`journal_mode = WAL`, `synchronous = NORMAL`, `busy_timeout = 5000`, `foreign_keys = ON`), and a `migrate()` entry point.

### Portable SQL

The client does not translate SQL. Instead, code that must run on both backends follows these rules; anything outside them is written twice and selected by `dialect`.

| Topic | Rule |
| --- | --- |
| Identifiers | Lowercase `snake_case`, unquoted. |
| Primary keys | `TEXT` ids generated by the application (ULID). No auto-increment on portable tables. |
| Timestamps | `BIGINT` milliseconds since epoch. No `DATETIME`, no timezone columns. |
| Booleans | `INTEGER` 0/1 in SQLite, `BOOLEAN` in PostgreSQL, declared through the migration helper. Reads come back as `0`/`1` on SQLite and `true`/`false` on PostgreSQL, so compare with `== 1 \|\| === true` or bind `true`/`false` and let the driver convert. |
| JSON | `TEXT` in SQLite, `JSONB` in PostgreSQL. Applications serialise and parse; no JSON operators in portable queries. |
| Upserts | `INSERT … ON CONFLICT (…) DO UPDATE SET …`. Supported identically by both. |
| Returning | `RETURNING` is supported by both. |
| Pagination | `LIMIT ? OFFSET ?`. |
| Not portable | `PRAGMA`, `AUTOINCREMENT`, `SERIAL`, `ILIKE`, `->>` JSON paths, `strftime`, `now()`. |

The migration helper covers the two type differences so that most migrations are a single string:

```ts
migrations: [
  { id: "001-notes", up: (t) => `
      CREATE TABLE notes (
        id         TEXT PRIMARY KEY,
        body       TEXT NOT NULL,
        pinned     ${t.bool} NOT NULL DEFAULT ${t.false},
        meta       ${t.json},
        created_at BIGINT NOT NULL
      )` },
  { id: "002-notes-index", up: `CREATE INDEX notes_created ON notes (created_at DESC)` },
  { id: "003-fts", sqlite: `CREATE VIRTUAL TABLE notes_fts USING fts5(body)`,
                   postgres: `CREATE INDEX notes_body_fts ON notes USING gin (to_tsvector('simple', body))` },
]
```

Applied migrations are recorded in `_migrations (id, applied_at)`. Migrations are append-only and additive: new tables, new nullable columns, new indexes. Dropping or renaming is done by adding a new column or table and migrating data in application code, then removing the old one in a later release. This is the same rule the scheduler store follows today.

### Concurrency

SQLite has one writer at a time. WAL mode lets readers proceed during a write, and `busy_timeout` makes a second writer wait instead of failing. The rule for apps is: one long-lived process owns each SQLite file. Other processes reach the data through that app's HTTP API, never by opening the file. Short-lived tools (backup, a one-off script) may open it read-only.

PostgreSQL removes that constraint. Bun's client keeps a small pool per `openDatabase` call; the default of a few connections is enough for a single-machine app. Apps that need more set it in their own URL (`?max=10`).

### How an app gets a database

The contract between an app and ai-space is a URL, not a library. The flow is the same for every language:

1. **Declare.** The app lists the databases it needs in `space.yaml` (`storage.database: sqlite` for the common single-database case; a `databases:` list when it needs more than one).
2. **Provision.** On sync ai-space creates what is missing: the file `<workspace>/data/<app>/<name>.db` for SQLite, or a database `<app>_<name>` plus a role with a generated password for PostgreSQL, created through `SPACE_PG_ADMIN_URL`. Existing databases are left exactly as they are; sync never drops or rewrites.
3. **Hand over.** ai-space writes `<workspace>/data/<app>/space.env` (mode 600) with one variable per database: `DATABASE_URL` for the database named `main`, `DATABASE_URL_<NAME>` for the others.
4. **Open.** The app reads the variable and opens it with whatever driver it already uses: `bun:sqlite` or Bun's `SQL` in TypeScript, `sqlite3` or `psycopg` in Python, `database/sql` in Go. TypeScript apps may use ai-space's `openDatabase` for the pragmas and migration helper, but nothing requires it.
5. **Own the schema.** The app creates its tables and runs its migrations. ai-space never reads or writes app tables; the only time it opens an app database is the read-only snapshot during backup.

How the variables reach the app process:

| App runs as | Mechanism |
| --- | --- |
| systemd unit | `EnvironmentFile=%h/.ai-space/data/<app>/space.env` next to the app's own `EnvironmentFile`. |
| scheduler `command` or `agent` target | Merged automatically, the same way the app's `.env` is merged today. |
| a shell, a script, a test | `bun src/index.ts env <app>` prints the variables in `export` form. |
| anything else | `GET /api/apps/:app/storage` returns the provisioned names, backends and paths. PostgreSQL passwords are not in the response; they only exist in `space.env`. |

Databases created at runtime, for example a scratch database an agent needs for one conversation, go through `POST /api/apps/:app/databases { name, backend? }`. They are provisioned by the same code, appear in `space.env` on the next write, and are marked `source: api` so a manifest re-sync does not treat them as orphaned. Removing a database is never a side effect of sync or of an API call: a name that disappears from the manifest is marked orphaned and kept, and `bun src/index.ts storage rm <app> <name>` moves the data aside as `<name>.removed-<ts>` rather than deleting it.

Ownership, in one line each:

- The app owns the schema, the migrations and the data.
- ai-space owns the location, the credentials, the backups and the inventory of what exists.
- Nobody else opens the file. Other apps reach the data through the owning app's HTTP API.

Alternatives considered and rejected:

| Alternative | Why not |
| --- | --- |
| One shared `space.db` with a table prefix per app | SQLite has one writer per file; every app would contend for it, and one corrupt file takes every app down. Backups and removal could no longer be per app. |
| ai-space as a database proxy (apps send SQL over HTTP) | An extra hop on every query, and a second implementation of every driver feature (transactions, streaming, types). Files get an HTTP API because they have a natural HTTP shape; rows do not. |
| Apps create their own files wherever they like | Works until backups, disk accounting and migration to another machine are needed. The manifest declaration costs one line and gives all three. |
| A PostgreSQL schema per app inside one database | Fine technically, but a database per app keeps `pg_dump`, roles and removal one-to-one with apps, and matches the SQLite layout. |

## Blobs

### Backends and configuration

| URL | Backend |
| --- | --- |
| `file:///abs/dir` | Filesystem. Default. Keys map to paths under the directory. |
| `s3://bucket/prefix` | Any S3-compatible service through Bun's built-in `S3Client`. Endpoint, region and credentials come from `SPACE_S3_ENDPOINT`, `SPACE_S3_REGION`, `SPACE_S3_ACCESS_KEY_ID`, `SPACE_S3_SECRET_ACCESS_KEY`. |

`SPACE_BLOB_URL` sets ai-space's own store (default `file:///<workspace>/data/blobs`). A per-app store is either `<workspace>/data/<app>/blobs` or `s3://<bucket>/<prefix>`, chosen per app in `space.yaml`. A separate `SPACE_BACKUP_URL` may point backups at a different bucket or account so that a compromised app credential cannot reach the backups.

### How an app gets a blob store

Implemented today; the same shape as databases:

1. **Declare.** `storage.blobs: file` or `storage.blobs: s3` in `space.yaml`. The mapping form names a bucket other than `SPACE_S3_BUCKET` or a prefix other than `<app>/`; `prefix: ""` hands the app the bucket root, for an app that already owns a bucket with its own layout.
2. **Provision.** On sync ai-space creates `<workspace>/data/<app>/blobs/` for `file`. For `s3` it resolves bucket and prefix, runs one `list` call with the `SPACE_S3_*` credentials the first time the store (or a new bucket/prefix) is declared, and refuses the sync if that fails. Nothing is written to the bucket, and a store that was already recorded is not probed again, so a flaky bucket does not stop a later boot.
3. **Hand over.** `space.env` gains `BLOB_URL` (`file:///…/blobs` or `s3://bucket/prefix/`) and, for `s3`, the `S3_*` variables above. `GET /api/apps/:app/storage` shows backend, bucket, prefix or path, never the keys.
4. **Use.** The app opens the store with whatever client it already has: `Bun.s3` picks the `S3_*` variables up by itself, the AWS SDK and boto3 take them as constructor arguments, a shell script can call `aws s3` with them. Keys are `prefix + key`; the app owns everything under its prefix and nothing outside it. Switching backends is refused by sync, like databases; a bucket or prefix change is accepted and logged, and the app is responsible for moving objects.
5. **Orphaning.** A store that leaves the manifest is marked orphaned, dropped from `space.env` and kept; no object is deleted.

Credentials are shared by every `s3` store on the machine (`SPACE_S3_ACCESS_KEY_ID` / `SPACE_S3_SECRET_ACCESS_KEY` in the workspace `.env`). A token scoped to one bucket therefore serves one app; an account-wide token serves all. Per-app tokens are a later addition if that separation is needed.

### Managed store (design)

The rest of this section describes the blob API ai-space will offer on top of the provisioned stores, for command and agent targets and for apps that prefer an HTTP API over an S3 client. It is not implemented yet.

#### Keys and metadata

Keys are opaque strings with `/` separators. The recommended layout is `<kind>/<yyyy>/<mm>/<ulid>.<ext>`, for example `images/2026/09/01J7…3F.webp`. The original filename is metadata, never part of the key, so user input cannot shape paths.

Every put also writes a row to the `blobs` table in ai-space's database:

| Column | Meaning |
| --- | --- |
| `app`, `key` | Identity. Unique together. |
| `size`, `content_type`, `sha256` | From the upload. `sha256` is computed while streaming. |
| `filename`, `tags` | Optional metadata supplied by the app. |
| `created_at`, `deleted_at` | Soft delete first; the object is removed by the prune job after a grace period. |

The index makes listing, quota checks and duplicate detection a database query instead of an S3 `LIST`, and it is what the backup job reads to know which filesystem objects exist. `sha256` lets an app deduplicate uploads (`findBySha`) without a second copy.

#### Interface

```ts
const blobs = await openBlobs(url);
await blobs.put(key, stream | Blob | Uint8Array, { contentType, filename?, tags? });
const file = await blobs.get(key);            // Bun.file-like: .stream(), .arrayBuffer(), .size, .type
await blobs.head(key);                        // metadata without the body
await blobs.delete(key);                      // soft delete; prune removes the bytes later
for await (const entry of blobs.list({ prefix, after })) …
blobs.presign(key, { method: "GET" | "PUT", expiresIn, contentType? });   // s3 only; fs returns a signed ai-space URL
```

Rules:

- **Stream everything.** Uploads go from the request body straight to disk or to a multipart S3 upload (`S3File.writer` with a 5 MB part size). Downloads are served from a stream with `Range` support so video seeks work. Memory per transfer is one part, not one file.
- **Verify then commit.** The object is written under a temporary key (`.tmp/<ulid>`), the hash and size are checked against what the client declared, then it is renamed or copied to the final key and the index row is inserted. A crashed upload leaves only a temporary object, which prune removes.
- **Large transfers bypass ai-space where possible.** With the S3 backend, the HTTP API returns presigned URLs and the browser talks to the bucket directly. With the filesystem backend, ai-space serves the bytes itself; this is fine on a LAN and behind a tunnel, but it is the reason S3 is recommended once video is involved.

#### HTTP API

```
POST   /api/blobs/:app                     multipart or raw body; headers carry content-type, x-filename
GET    /api/blobs/:app/*key                stream, honours Range; 302 to a presigned URL on s3
HEAD   /api/blobs/:app/*key
DELETE /api/blobs/:app/*key
GET    /api/blobs/:app?prefix=&after=      index listing
POST   /api/blobs/:app/presign             { key, method, contentType, expiresIn }

GET    /api/apps/:app/storage              provisioned databases and blob stores (no secrets)
POST   /api/apps/:app/databases            { name, backend? }  provision a database at runtime
```

Mutating routes require the bearer token, as with the scheduler. An app that runs its own process and wants to serve files directly uses the TypeScript module or its own S3 client with the credentials from `space.env`; the HTTP API exists for command and agent targets and for apps without an S3 library.

## Backups

### What is backed up

| Source | Method | Notes |
| --- | --- | --- |
| SQLite database | `VACUUM INTO '<staging>/<db>.db'` on the live file | Consistent snapshot under WAL, no lock on writers, output is already compacted. |
| PostgreSQL database | `pg_dump -Fc` | Requires `pg_dump` on the machine; the task fails loudly if it is missing. |
| Filesystem blobs | `tar` of the blob directory, filtered by the index | Objects not in the index (temporary uploads) are skipped. |
| S3 blobs | Not copied by default | The bucket is already off-machine. Optional `copy: true` mirrors to `SPACE_BACKUP_URL` with server-side copy. |
| `space.yaml`, `space.env` | Included | Small, and needed to restore an app in one step. |
| Workspace `.env` | Never | Secrets stay out of backups. Recreate from the password manager. |

Snapshots are compressed with zstd, named `backups/<app>/<yyyy>/<yyyy-mm-ddThh-mm>Z.tar.zst`, uploaded to `SPACE_BACKUP_URL` (falls back to `SPACE_BLOB_URL`), and recorded in a `backups` table with size, sha256, duration and which sources were included. The staging directory is emptied afterwards, so peak disk use is one uncompressed snapshot.

### Schedule and retention

Backups are ordinary scheduler tasks. Declaring `backup` in `space.yaml` makes the storage module register a `command` task named `backup` for that app; the schedule and retention come from the manifest. ai-space backs up its own database on `SPACE_BACKUP_SCHEDULE` (default `0 3 * * *`).

Retention is expressed as counts, not days, so a machine that was off for a week does not delete everything on the first run back: keep the last `daily` snapshots, the last `weekly` (first of each ISO week) and the last `monthly`. Prune runs after every successful upload and only deletes objects that the `backups` table lists; unknown objects in the prefix are left alone.

### Verification and restore

A snapshot that was never opened is not a backup. Once a week the `backup-verify` task downloads the newest snapshot of each app into staging, opens the SQLite copy and runs `PRAGMA integrity_check` (or `pg_restore --list` for PostgreSQL), checks the tar listing against the manifest inside the archive, and records the result. A failed verification marks the snapshot in the table and the task fails, which surfaces in the scheduler's task list.

Restore is a CLI command, not an API route, because it replaces live data:

```
bun src/index.ts restore <app> [--at 2026-09-01T03-00Z] [--to <dir>]
```

Without `--to` it stops the app's unit, moves the current data aside as `<app>.pre-restore-<ts>`, unpacks the snapshot, and starts the unit. With `--to` it only unpacks, which is the path for inspecting old data or migrating to another machine.

## Registering storage in `space.yaml`

```yaml
name: my-app
storage:
  database: sqlite            # short form: one database named "main"; sqlite (default) | postgres
  # databases:                # long form when an app needs several
  #   - { name: main, backend: postgres }
  #   - { name: cache, backend: sqlite }
  blobs: s3                   # none (default) | file | s3
  # blobs:                    # mapping form
  #   backend: s3
  #   bucket: media           # default SPACE_S3_BUCKET
  #   prefix: ""              # default <app>/; "" = bucket root
  backup:
    schedule: "0 3 * * *"
    timezone: UTC
    keep: { daily: 7, weekly: 4, monthly: 6 }
    include: [database, blobs]   # blobs on s3 are skipped unless copy: true
```

On sync ai-space:

1. Creates `<workspace>/data/<app>/` and, for each declared database, the SQLite file or the PostgreSQL database and role.
2. Creates the blob directory, or checks once that the bucket is reachable with the configured credentials.
3. Writes `space.env` with `DATABASE_URL`, `BLOB_URL`, `SPACE_APP_DATA_DIR` and the `S3_*` variables.
4. Registers the `backup` task with the scheduler when `backup` is declared.

Sync is idempotent. Changing `database` from `sqlite` to `postgres` provisions the new database but does not move data; that is the app's migration to run, and the old file stays until removed by hand.

## Configuration

```
SPACE_DB_URL              ai-space's database        default sqlite:///<workspace>/data/space.db
SPACE_BLOB_URL            ai-space's blob store       default file:///<workspace>/data/blobs
SPACE_BACKUP_URL          where snapshots go           default SPACE_BLOB_URL
SPACE_BACKUP_SCHEDULE     ai-space's own backup        default "0 3 * * *"
SPACE_PG_ADMIN_URL        superuser URL used only to create per-app databases and roles
SPACE_S3_ENDPOINT         e.g. https://<account>.r2.cloudflarestorage.com, http://127.0.0.1:9000
SPACE_S3_REGION           auto for R2; a real region for AWS
SPACE_S3_ACCESS_KEY_ID
SPACE_S3_SECRET_ACCESS_KEY
SPACE_S3_BUCKET           default bucket for s3 blob stores when the app does not name one
```

All of these live in the workspace `.env`, so app manifests never contain credentials.

## Module layout

```
src/space/storage/
├── types.ts        Dialect, DatabaseSpec, BlobSpec, StorageSpec (the space.yaml shape), inventory rows
├── db.ts           openDatabase(url), migrate(), dialect helpers
├── spec.ts         parsing of the storage: section
├── storage.ts      per-app database / blob store provisioning, inventory tables, space.env writer

```

The scheduler's `store.ts` moves onto `openDatabase` in the same change that introduces `db.ts`; its schema becomes the first migration set. That is the proof that the database half works before any app depends on it.

## Failure modes considered

| Situation | Behaviour |
| --- | --- |
| Two processes open one SQLite file for writing | The second waits up to `busy_timeout`, then fails with `SQLITE_BUSY`. The fix is architectural: one owner per file. |
| Upload interrupted | Only a temporary object exists; no index row. Prune removes it after an hour. |
| Client declares a wrong size or hash | Upload rejected with 422 before the object is committed. |
| S3 unreachable | Puts fail fast and the app sees the error; nothing is queued locally. Backups fail as tasks and back off through the scheduler. |
| Disk full during snapshot | `VACUUM INTO` fails, the task errors, live data untouched. The staging directory is on the same disk by design so the check happens before any upload. |
| Snapshot corrupt | Detected by the weekly verify task; the snapshot is marked and prune keeps the previous good one. |
| `pg_dump` version older than the server | `pg_dump` refuses; the task fails with its message rather than producing a partial dump. |
| Restore on the wrong machine | `--to` extracts without touching live data; the in-place path refuses when the app directory does not exist. |

## Migrating an app

1. Declare `storage` in the app's `space.yaml` and re-sync. Read `DATABASE_URL` and `BLOB_URL` from `space.env` instead of hard-coded paths.
2. For an app that already has a SQLite file: move it to `<workspace>/data/<app>/app.db` (or set `database: sqlite` and copy the file in before the first start). Nothing else changes; the app keeps its own schema and driver.
3. For an app that already keeps objects in a bucket: declare `blobs: { backend: s3, bucket: <its bucket>, prefix: "" }` (or the prefix it already uses), point the app's S3 client at `BLOB_URL` and the `S3_*` variables instead of its own credential names, and keep the old names as a fallback for one release. Files that live in the app directory today (uploads, generated images, exports) move into the store with a one-off copy; the app records the new key where it used to store a path.
4. Turn on `backup` and check the first snapshot in `/api/tasks` and the `backups` table. Run a `restore --to` into a temporary directory once to confirm the round trip.
5. Consider `database: postgres` only when the app needs several writers or lives on more than one machine. The rules in [Portable SQL](#portable-sql) make the switch a configuration change for TypeScript apps that used the client from the start.

## Rollout order

1. Done: `db.ts` + `migrate()`, `spec.ts`, `storage.ts` (provisioning, inventory, `space.env`), `api.ts`, the `env` command, and the scheduler passing `space.env` to command and agent targets. SQLite is covered by tests; PostgreSQL provisioning is implemented but only exercised by hand until CI has a container.
2. Done: `storage.blobs` (file and s3), the reachability probe, `BLOB_URL` and `S3_*` in `space.env`, the inventory table and `describe`.
3. The scheduler store on top of `db.ts`.
4. `blobs.ts`: the managed store with the index, filesystem and S3 backends, HTTP routes and presigning.
5. `backup.ts`: snapshot and upload, then prune, then verify, then restore.
6. `storage rm` and the `backup` key of the `space.yaml` section.
