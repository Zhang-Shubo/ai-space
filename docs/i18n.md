# Languages

The panel speaks the operator's language. English and Chinese are supported today; adding a language is one dictionary file and one manifest key.

Status: implemented for the panel (tiles, settings, chat, tasks, widgets), the relative times the panel formats, and the text apps declare in `space.yaml`. Notifications, the CLI (`setup`) and agent prompts stay in English: their readers are the operator's chat channel and the runtime, not a browser with a language setting.

## Why in the browser

Everything the panel shows is either text the panel itself owns (headings, buttons, hints, statuses) or text an app declares in its manifest (title, description, agent and widget titles). Neither needs the server to know the reader's language:

- **The server serves one page to every browser.** A panel is opened from a laptop in one language and a phone in another; the hub merges peers whose operators may not share a language. Resolving text server-side would need a language per request, a cache key per language for widgets and peer snapshots, and a way for a peer to know the hub's readers. Sending every language the manifest declares and choosing in the browser needs none of that, and the payload grows by a few strings per app.
- **The manifest is the registration.** An app that wants a Chinese title says so in its own `space.yaml`, next to the English one, and the change travels with the app, the same way `title` and `icon` do ([app-spec](app-spec.md)).
- **No translation service.** Text the panel does not have in the reader's language falls back to the manifest's plain field, and then to English. Nothing is machine-translated, so nothing is invented.

## Choosing the language

The panel resolves the language once per page load, in this order:

1. The preference saved in the browser (`panel-lang` in `localStorage`), set from the **Language** row in Settings.
2. The browser's own languages (`navigator.languages`): the first entry whose primary tag the panel knows. `zh-CN`, `zh-TW` and `zh-Hant` all mean Chinese; anything else means English.
3. English.

Changing the language in Settings takes effect immediately and sets `<html lang>` so the browser picks matching fonts and hyphenation. The preference lives in the browser like the theme and the desk pet; nothing is stored on the server.

## What is translated

| Text | Where it comes from | In the reader's language when |
| --- | --- | --- |
| Panel strings: headings, buttons, switches, hints, statuses, placeholders, dialogs | `src/web/i18n.ts`, one dictionary per language | always (every key exists in every dictionary; a test enforces it) |
| Relative times and durations ("3 min ago", "in 2 h", "every 30m", "once at …") | `src/web/api.ts` helpers, which take the language | always |
| App title and description, agent title and description, widget title | the app's `space.yaml`: the plain field, or the `i18n:` section | the manifest declares that language; otherwise the plain field |
| The space agent ("Base") | built in | always |
| Names: app names, agent ids, task names, tool names, ports, model names | manifests, the runtime | never: they are identifiers |
| Widget items, chat replies, task output and errors | the apps and the runtime | whatever the app or the model wrote |

Manifest names (`name:`) are never translated: they are keys in URLs, layout order, task ids and the peer prefix.

## The manifest: `i18n:`

An app adds translations of its display text in one top-level section, keyed by language:

```yaml
title: Notes
description: Personal notes with an agent that files and searches them.
agents:
  - name: librarian
    title: Librarian
    description: Files and finds notes.
widgets:
  - name: recent
    title: Notes · Recent

i18n:
  zh:
    title: 笔记
    description: 个人笔记，带一个归档和检索的智能体。
    agents:
      librarian: { title: 图书管理员, description: 归档并查找笔记。 }
    widgets:
      recent: { title: 笔记 · 最近 }
```

Rules, in the strict spirit of the rest of the manifest (a bad `i18n:` rejects the whole app):

- Keys of `i18n` are language tags: two or three lowercase letters, optionally followed by subtags (`zh`, `zh-Hant`, `pt-BR`). The panel matches on the primary tag today.
- Each language is a mapping with optional `title`, `description`, `agents`, `widgets`. Nothing else.
- `agents` and `widgets` map an existing agent or widget **name** to a mapping with `title` (and `description` for agents). Naming an agent or widget the manifest does not declare is an error, so a rename cannot leave a stale translation behind.
- Every translated value is a non-empty string. Untranslated fields are omitted, not left empty; the plain field shows instead.
- The plain `title` and `description` stay the source of truth: they are what notifications tag messages with, what agents are told about the app, what a browser with an unknown language shows.

## Through the API

The panel API keeps `title` and `description` as plain strings and adds an optional `i18n` object next to them, on apps, agents, widgets and services:

```json
{ "name": "notes", "title": "Notes", "description": "Personal notes …",
  "i18n": { "zh": { "title": "笔记", "description": "个人笔记 …" } } }
```

Only languages that translate at least one field of that entry appear; an app without an `i18n:` section has no `i18n` key, so existing clients and scripts see exactly what they saw before. Peers pass the field through unchanged: a hub shows a peer's apps in the hub reader's language when the peer's manifests declare it, without any peer-side setting. The browser picks `i18n[lang].title ?? title`.

## Apps

An app's own pages run on their own origin and cannot read the panel's preference. By default they see only the browser's language (`navigator.language`, `Accept-Language`), which is the panel's default too, so the two agree unless the operator changed the language in Settings. The panel hands its choice to an app in two places, as a hint the app may use or ignore:

- **Embed widgets** receive `lang` next to `theme` in their query string: the iframe loads `/api/widgets/:app/:name/embed?theme=dark&lang=zh` and ai-space forwards both to the page (`lang` only when it is a language tag, so a page never sees anything else). This is the counterpart of the theme contract in [app-spec](app-spec.md#widgets).
- **App pages** opt in with a `{lang}` placeholder in the manifest's `url` query, `https://my-app.example.com/?lang={lang}`. The panel fills it when a tile or a widget's "View all" link is opened; a `url` without the placeholder is opened unchanged, so an app that does not know the parameter is never handed one. The placeholder belongs in the query: a URL parser percent-encodes braces in a path, and while the panel also fills the encoded form, links an app derives from its own path would carry the literal. An app that wants the choice to stick stores the parameter it received in its own `localStorage`.

Widget items, chat replies and task output are written by the apps and the runtime; the panel shows them as they are.

## Module layout

```
src/web/i18n.ts        Lang, the dictionaries (en, zh), detectLang, loadLang/saveLang, translate,
                       LangContext + useLang() (returns lang and t), localized() for manifest text,
                       withLang() for the {lang} placeholder in app urls
src/web/api.ts         relTime, untilTime, fmtDuration, scheduleText take the language
src/space/scheduler/manifest.ts   parses `i18n:` (ManifestI18n)
src/space/panel/view.ts, widgets.ts, agents/api.ts   put `i18n` on the views
```

Panel components call `const { lang, t } = useLang()` and write `t("settings.darkMode")`; text with a value uses placeholders, `t("tasks.summary", { active, total })`. Keys are grouped by screen (`apps.*`, `settings.*`, `chat.*`, `tasks.*`, `widget.*`, `time.*`, `status.*`); the English dictionary defines the key set and the type checker holds the other dictionaries to it.

## Adding a language

1. Add the tag to `LANGS` in `src/web/i18n.ts` with its native name for the Settings row, and a dictionary with every key of `en` (the type checker lists the missing ones).
2. Extend `detectLang` if the browser tag differs from the dictionary key in a way the primary-tag match does not cover.
3. Translate the space agent's `i18n` entry in `src/space/agents/api.ts`.
4. Apps add the language under `i18n:` in their own manifests when they want to; nothing in ai-space has to change for that.

## Failure modes considered

- A manifest names a language the panel has no dictionary for: the panel still shows that manifest's text when the reader's browser is set to that language; the panel's own strings fall back to English. Nothing is rejected.
- A dictionary misses a key: the type checker fails the build, and a test compares the key sets so an untyped edit is caught too. At runtime an unknown key renders the key itself, never an empty string.
- A translation is longer than the English: tiles truncate their names with an ellipsis as they already do; dialogs and rows wrap. No layout depends on the English length.
- The browser has no `localStorage` (a privacy mode that throws): the language is detected from the browser on each load and cannot be pinned; the panel still works.
- An old peer answers without `i18n` fields: its entries show their plain text. A new peer answering an old hub: the hub's browser ignores the extra field.
